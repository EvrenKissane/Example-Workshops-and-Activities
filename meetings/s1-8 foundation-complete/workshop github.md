# **Do Quantum**: GitHub Collaboration Workshop

**Purpose**
Practice collaborative software development while establishing the workflow your team will use throughout the program.
This workshop should help you learn how distributed teams coordinate work, manage project history, and contribute to a shared repository using Git and GitHub.

**Duration**
75 Minutes

# Instructions

**Goal**
* Set up the software and accounts required for future project work.
* Learn the basic GitHub workflow used by research and engineering teams.
* Practice collaborating on a shared repository with your teammates.
* Experience how branches, adds, commits, pulls, pushes, and pull requests work together.

**Steps**
1. Install prerequisites to start collaborating.
    1. Verify GitHub account access.
    2. Make a team repository.
    3. 'Clone' the team repository.
    3. Use VSCode as the IDE (Integrated development environment).
    4. Verify that Git commands work successfully.
    Industry standard is using Git for version control and VSCode for IDE. We'll store the versons in GitHub, but GitLab is also frequently used in industry.
2. Create a remote respository to work with your teammates.
    1. Create a new GitHub repository.
    2. Add all teammates as collaborators with edit permissions.
    3. 'Clone' the repository in the IDE.
    4. Confirm everyone can see and access the project.
3. Stage, Commit, and Push to practice recording changes in project history.
    1. Create a file introducing yourself.
    2. Add your file to the repository.
    3. 'Stage' your changes.
    4. 'Commit' your changes with a descriptive message.
    5. 'Push' your changes to GitHub.
4. Pull from remote repository to observe how changes made by teammates propagate through a project.
    1. Wait for teammates to push their changes.
    2. 'Pull' the latest version of the repository.
    3. Verify that everyone's files appear on eachothers local repository.
    4. Discuss and resolve any conflicts or synchronization issues that occur.
5. Create Feature Branches to practice the workflow that will be used for future project development.
    1. Create a personal feature branch on GitHub or VSCode (branch to develop your feature in isolation).
    2. Make a new change to the repository.
    3. 'Commit' your changes to the branch.
    4. 'Push' your changes to the branch, thereby the branch, to GitHub.
6. Practice coordinating work across multiple contributors.
    1. 'Fetch' branches teammates made from the remote repository.
    2. Examine branches created by teammates.
    3. Discuss what each teammate changed.
    4. Verify that everyone's work exists in isolation.
7. Create a Pull Requests to integrate isolated work into a shared project.
    1. Open a Pull Request for your branch.
    2. Describe what was changed and why.
    3. Review a teammate's Pull Request.
    4. Merge approved changes into the main branch.

# Submission
1. Verify that every participant has:
   * Successfully cloned the repository.
   * Created at least one commit.
   * Pulled changes from teammates.
   * Created a feature branch.
   * Opened a Pull Request.
2. Ensure all Pull Requests have been merged.
3. Confirm the repository is accessible to all team members.

# Checklist

**Repository Setup**
* Every participant can access the repository.
* IDEs are configured correctly.
* Team members can successfully communicate with GitHub.

**Collaboration**
* Participants understand the difference between Git and GitHub.
* Repository history shows detailed commit messages.
* Participants understand the difference between local and shared repositories.

**Branch Workflow**
* Feature branches are created and used correctly.
* Changes are isolated before integration.
* Participants understand the purpose of branching.

**Pull Requests**
* Pull Requests clearly describe changes.
* Team members review each other's work.
* Contributions are merged successfully.

# Tips
1. Remote repositories are shared repositories
2. Make small changes so they are easy to understand.
3. Write commit messages that explain what changed.
4. Pull everytime you open your local repository to avoid conflicts.
5. Git is not just a software tool, it's a communication tool for teams.
